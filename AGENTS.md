# AGENTS.md — Hirepath operating manual

This is the single source of truth for anyone (human or agent) working in this
repo. It is deliberately tool-agnostic: nothing here depends on a particular IDE
or AI assistant. `CLAUDE.md` just points here.

## What Hirepath is

A **local-first job-hunting companion**. v1 does one job, conversationally: the
user brings a resume and a job description, and Hirepath scores the match, finds
the gaps, and then keeps talking about it. Everything runs on the user's machine
— a local ASP.NET Core API plus a local SQLite file. No accounts, no cloud.

**Chat is the interface.** The app opens to a conversation, not a dashboard. The
assistant operates the app through tools; its answers render as interactive
widgets, not walls of text. Every tool also has a plain UI path.

## Toolchain

- **.NET 10 SDK** (C# 14), backend.
- **Node 22.22+ / 24.x**, **Angular 22**, frontend.
- SQLite (bundled with EF Core; no server to install).

## Commands

Run from the repo root unless noted.

| Task | Command |
| :--- | :--- |
| Run everything (API + web) | `./run.ps1` (Windows) or `./run.sh` |
| All verification gates | `./verify.ps1` or `./verify.sh` |
| Build backend | `dotnet build Hirepath.slnx` |
| Test backend | `dotnet test Hirepath.slnx` |
| Format backend | `dotnet format Hirepath.slnx` |
| Add a migration | `dotnet dotnet-ef migrations add <Name> --project src/Hirepath.Infrastructure --startup-project src/Hirepath.Api --output-dir Persistence/Migrations` |
| Frontend dev server | `cd src/Hirepath.Web && npm start` |
| Frontend tests | `cd src/Hirepath.Web && npm run test:ci` |
| Frontend lint | `cd src/Hirepath.Web && npm run lint` |
| Regenerate API client | `cd src/Hirepath.Web && npm run generate:api` |
| Production web build | `cd src/Hirepath.Web && npm run build` |

Ports: API `https://localhost:7180`, web `http://localhost:4200` (proxied to the
API). Both configurable — see `appsettings.json` and `proxy.conf.json`.

## Architecture rules (do not break these)

- **Dependency rule:** `Domain` ← `Application` ← `Infrastructure` / `Api`.
  `Domain` references nothing. Scoring math, keyword coverage, and
  experience-gap calculations are **pure functions in `Domain`**, unit-tested
  without a database or a model.
- **Prompts live in `Hirepath.Application/Prompts/*.md`**, versioned, loaded with
  named parameters. No prompt strings inline at call sites.
- **Tools are declared once** in `Application` as `AIFunction`s over the same
  use-case handlers the REST endpoints call. One implementation, two entry
  points (chat + HTTP). Never two copies.
- **`FakeChatClient` only in tests.** No automated test touches the network. It
  also powers Demo Mode.
- **Model IDs are configuration**, never constants in code.
- **Widgets:** every widget name maps to exactly one Angular component via a
  registry; payloads are produced server-side by tool handlers, never by the
  model writing JSON. See `docs/ARCHITECTURE.md`.
- **The generated API client** (`src/Hirepath.Web/src/app/core/api/`) is
  git-ignored and regenerated by NSwag. Never hand-edit it.
- **Secrets never enter the repo.** API keys live in the local SQLite settings
  row (or `dotnet user-secrets` / env vars in dev). Never logged, never
  committed.

## Conventions

- C#: `nullable` + `TreatWarningsAsErrors` on. File-scoped namespaces. Standard
  .NET style enforced by `.editorconfig` + `dotnet format`. Central package
  versions in `Directory.Packages.props`.
- Angular: standalone components, **signals** for state, **zoneless** change
  detection, new control flow (`@if`/`@for`), `inject()` over constructor DI,
  one `*-store.ts` signal store per feature. Enforced by ESLint + Prettier.
- Keep files small (~300 lines). Organise by feature, not by file type.
- Boring and readable beats clever.

## Definition of done (every feature)

Works with a real provider, works in Demo Mode, has all four async states
(loading / empty / error / success), is keyboard-navigable, passes every gate in
`./verify.ps1`, and is marked `shipped` in `docs/FEATURES.md`.

## Doc-update requirement

A phase is not complete until, in the same commit: `README.md`,
`docs/FEATURES.md`, `docs/ROADMAP.md`, `docs/ARCHITECTURE.md`, `CHANGELOG.md`,
and any new ADR under `docs/decisions/` are updated. Write an ADR whenever you
extend or deviate from `BUILD_PROMPT.md`.
